## 五、核心技术要点

### 5.1 TEST_END 修正的意义

原设计将 2026-01-01 之后的数据也划入 `test` 集，导致评估口径比周二基准多了约 3 个月的数据。这部分数据（1月-3月）可能是秋冬季节的低辐照期，与夏末（9月）差异较大，混入后拉低了整体 ratio。

修正后，`test` 集严格限定为 `2025-09-01 <= time < 2026-01-01`，与周二基准完全对齐。

### 5.2 BaselineTotal 的设计逻辑

`power_pred`（ML 模型输出）系统性低估的原因是：模型在训练集上学到的 GHI→功率映射存在偏差，这在辐照度反演（`pred_baseline`）中已被纠正。`pred_baseline` 直接利用辐照度物理模型，输出总量与实际几乎一致（ratio ≈ 0.9998）。

通过 Guard 机制，将 `BaselineTotal` 作为候选版本，取代原有的 V0/V1，14 个时段全部胜出，说明：
- 在 valid 集（7-8月）上，BaselineTotal 的 score 综合最优
- 总量偏差修复（ratio 从 0.73 → 0.9998）远超过站点级精度的微小代价

### 5.3 数据去重的重要性

原始数据在 2026-02-27 存在 (time, site_id) 重复行（781 行重复），导致 merge 时行数爆炸。去重后 `build_final` 逻辑恢复正常。
